What are Retrievers?

📌 Core Definition A retriever is a component in LangChain that fetches relevant documents from a data source in response to a user's query. All retrievers in LangChain are Runnables — they follow the standard .invoke(query) interface.
Real-World Analogy

Think of a retriever like a librarian. You walk in and say "I need books about climate change." The librarian (retriever) knows the entire library (data source), searches intelligently, and hands you only the most relevant books (documents) — not the whole library.

🔧Key Properties

  • Fetches relevant documents, not all documents
  • Responds to a user query (string input)
  • Returns a list of Document objects
  • All retrievers are LangChain Runnables
  • Use .invoke(query) to call any retriever

⚙️How it Works (Internally)

  • Accepts a string query as input
  • Runs a function (fxn) against the data source
  • Returns multiple Document objects
  • Each Document has page_content + metadata
Runnable Interface query → fxn → List[Document]

Types of Retrievers

LangChain offers two main dimensions for classifying retrievers: by Data Source (where data comes from) and by Search Strategy (how results are selected).

📂 By Data Source

  • Wikipedia Retriever — Pulls from Wikipedia API
  • Vector Store Retriever — Uses embedded document vectors (Chroma, FAISS)
  • ArXiv Retriever — Fetches academic research papers

🔍 By Search Strategy

  • MMR (Maximal Marginal Relevance) — Diverse, non-redundant results
  • Multi-Query — LLM rewrites your query multiple ways
  • Contextual Compression — Compresses docs to only relevant content
Retriever Data Source Search Strategy Best For
WikipediaRetriever Wikipedia API Keyword / Semantic General knowledge queries
VectorStoreRetriever Local Vector DB Cosine Similarity Custom document collections
MMR Retriever Vector Store Marginal Relevance Diverse, non-redundant results
MultiQueryRetriever Vector Store LLM re-writing + Multi-search Ambiguous or broad queries
ContextualCompression Any base retriever LLM-based compression Long, mixed-content docs
ArxivRetriever ArXiv API Keyword Search Academic/research papers

Wikipedia Retriever

📖 Definition A Wikipedia Retriever queries the Wikipedia API to fetch relevant content for a given query. It requires no local document setup — the data source is Wikipedia itself.

WIKIPEDIA RETRIEVER FLOW

ipl / Query
→
Wikipedia API
→
Document Objects

How It Works

1

Receive a Query

You pass a natural language string e.g. "Albert Einstein" or "Geopolitical history of India and Pakistan"

2

Send to Wikipedia's API

The retriever forwards the query to Wikipedia's search API using the wikipedia Python package under the hood.

3

Retrieve Most Relevant Articles

Wikipedia returns the top-k most relevant articles (controlled by top_k_results parameter).

4

Return as LangChain Document Objects

Each article is wrapped in a LangChain Document with page_content (article text) and metadata.

Python 
# Install: pip install wikipedia langchain-community
from langchain_community.retrievers import WikipediaRetriever

# Initialize retriever with top_k and language
retriever = WikipediaRetriever(
    top_k_results=2,
    lang="en"
)

# Define your query
query = "the geopolitical history of india and pakistan from the perspective of a chinese"

# Get relevant Wikipedia documents
docs = retriever.invoke(query)

# Print retrieved content
for i, doc in enumerate(docs):
    print(f"\n--- Result {i+1} ---")
    print(f"Content:\n{doc.page_content}...")  # truncate for display
⚠️ Note The top_k_results parameter controls how many Wikipedia articles are fetched. Setting it too high may slow down your pipeline or exceed context limits. Start with 2–3.

Vector Store Retriever

The most common retriever in RAG (Retrieval-Augmented Generation) pipelines. It converts your documents into numerical vectors (embeddings) and stores them in a vector database, enabling fast semantic similarity search.

Real-World Analogy

Think of embeddings as GPS coordinates for meaning. Documents about similar topics get coordinates that are geographically close. When you query, the vector store finds documents whose "meaning coordinates" are nearest to your query's coordinates.

VECTOR STORE RETRIEVER — SETUP PIPELINE

Documents

→
Embedding
Model

→

→
Retriever

Python 
from langchain_community.vectorstores import Chroma
from langchain_openai import OpenAIEmbeddings
from langchain_core.documents import Document

# Step 1: Your source documents
documents = [
    Document(page_content="LangChain helps developers build LLM applications easily."),
    Document(page_content="Chroma is a vector database optimized for LLM-based search."),
    Document(page_content="Embeddings convert text into high-dimensional vectors."),
    Document(page_content="OpenAI provides powerful embedding models."),
]

# Step 2: Initialize embedding model
embedding_model = OpenAIEmbeddings()

# Step 3: Create Chroma vector store in memory
vectorstore = Chroma.from_documents(
    documents=documents,
    embedding=embedding_model,
    collection_name="my_collection"
)

# Step 4: Convert vectorstore into a retriever
retriever = vectorstore.as_retriever(search_kwargs={"k": 2})

# Query the retriever
query = "What is Chroma used for?"
results = retriever.invoke(query)

for i, doc in enumerate(results):
    print(f"\n--- Result {i+1} ---")
    print(doc.page_content)

⚙️ Key Parameters

  • k — Number of docs to retrieve (default: 4)
  • search_type — "similarity" or "mmr"
  • collection_name — Name of the Chroma collection
  • embedding — Embedding model to use

📦 Popular Vector Stores

  • Chroma — Lightweight, in-memory, easy to use
  • FAISS — Facebook's fast similarity search, great for large datasets
  • Pinecone — Managed cloud vector DB
  • Weaviate — Open-source, multi-modal support

Maximal Marginal Relevance (MMR)

🔮 Core Idea MMR is an information retrieval algorithm designed to reduce redundancy in retrieved results while maintaining high relevance to the query. It answers: "How can we pick results that are not only relevant to the query but also different from each other?"

Why Do We Need MMR?

❌ Problem: Regular Similarity Search

  • Results are all very similar to each other
  • Repeating the same information
  • Lacking diverse perspectives
  • Wastes context window with redundant content

✅ MMR Solution

  • Picks the most relevant document first
  • Then picks the next most relevant AND least similar to already selected docs
  • Continues until k documents are selected
  • Result: diverse but still relevant document set

🌍 Visual Example — Climate Change Query

Doc ID Content Regular Top-3 MMR Top-3
D1 "Climate change is causing glaciers to melt rapidly in the Arctic region." ✓ Selected ✓ Selected
D2 "Glaciers in the Arctic are melting at an alarming rate due to rising temperatures." ✓ Selected ✗ Too Similar to D1
D3 "Deforestation in the Amazon is accelerating global climate change." ✓ Selected ✗ Skipped
D4 "Climate change is increasing the frequency of wildfires in California." ✗ Not selected ✓ Diverse topic
D5 "Rising sea levels due to climate change threaten coastal cities." ✗ Not selected ✓ Different angle
Python — MMR with FAISS 
from langchain_community.vectorstores import FAISS

# Initialize embeddings & create FAISS vector store
embedding_model = OpenAIEmbeddings()
vectorstore = FAISS.from_documents(
    documents=docs,
    embedding=embedding_model
)

# Enable MMR in the retriever
retriever = vectorstore.as_retriever(
    search_type="mmr",              # <-- This enables MMR
    search_kwargs={
        "k": 3,                    # Top results to return
        "lambda_mult": 1          # Relevance-diversity balance
    }
)

query = "What is langchain?"
results = retriever.invoke(query)
🎛️ lambda_mult Parameter lambda_mult=1 → Full relevance (like standard similarity search)  |  lambda_mult=0 → Maximum diversity  |  lambda_mult=0.5 → Balanced (recommended default)

Multi-Query Retriever

🔍 Core Problem Solved Sometimes a single query might not capture all the ways information is phrased in your documents. A simple similarity search might miss documents that talk about those things but don't use the exact same words as your query.
Real-World Analogy

Imagine asking a librarian "How can I stay healthy?" — but all the best books use terms like "nutrition," "fitness routines," and "stress management." A smart librarian would search for all related phrasings, not just the literal words you said. That's Multi-Query.

❓ Original Query

"How can I stay healthy?"

Could mean:

  • What should I eat? ✓
  • How often should I exercise? ✓
  • How can I manage stress? ✓

🤖 LLM-Generated Sub-Queries

  1. "What are the best foods to maintain good health?"
  2. "How often should I exercise to stay fit?"
  3. "What lifestyle habits improve mental and physical wellness?"
  4. "How can I boost my immune system naturally?"
  5. "What daily routines support long-term health?"

How It Works — Step by Step

1

Takes Your Original Query

Your single natural language query is passed to the retriever.

2

Uses an LLM to Generate Sub-Queries

An LLM (e.g., GPT-3.5) generates multiple semantically different versions of your query.

3

Performs Retrieval for Each Sub-Query

Each generated sub-query is sent to the underlying vector store retriever independently.

4

Combines and Deduplicates the Results

All retrieved documents are merged into a single list, with duplicates removed.

Python — MultiQueryRetriever 
from langchain.retrievers.multi_query import MultiQueryRetriever
from langchain_openai import ChatOpenAI
from langchain_community.vectorstores import FAISS

# Create base similarity retriever
similarity_retriever = vectorstore.as_retriever(
    search_type="similarity",
    search_kwargs={"k": 5}
)

# Wrap it with MultiQueryRetriever using an LLM
multiquery_retriever = MultiQueryRetriever.from_llm(
    retriever=vectorstore.as_retriever(search_kwargs={"k": 5}),
    llm=ChatOpenAI(model="gpt-3.5-turbo")
)

# Query
query = "How to improve energy levels and maintain balance?"
results = multiquery_retriever.invoke(query)

print(f"Retrieved {len(results)} unique documents")
⚠️ Trade-off Multi-Query Retriever increases recall (finds more relevant docs) but costs more LLM API calls (one per sub-query generation + the LLM call for query generation itself). Use it when recall matters more than cost.

Contextual Compression Retriever

🗜️ Definition The Contextual Compression Retriever is an advanced retriever that improves retrieval quality by compressing documents after retrieval — keeping only the relevant content based on the user's query.

The Problem with Standard Retrievers

❌ Example: Query = "What is photosynthesis?"

"The Grand Canyon is a famous natural site. Photosynthesis is how plants convert light into energy. Many tourists visit every year."

  • The retriever returns the entire paragraph
  • Only one sentence is actually relevant to the query
  • The rest is irrelevant noise that wastes context window

✅ What Contextual Compression Does

"Photosynthesis is how plants convert light into energy."

Returns only the relevant part — trimmed by an LLM compressor.

D2 (full doc)
→

Query also sent to LLM to guide what is "relevant" in each document

How It Works

1

Base Retriever Fetches N Documents

A standard retriever (e.g., FAISS, Chroma) retrieves K documents using similarity search.

2

A Compressor is Applied to Each Document

An LLM compressor (e.g., LLMChainExtractor) processes each document along with the original query.

3

The Compressor Keeps Only Relevant Parts

The LLM extracts only the sentences/paragraphs that are relevant to the query.

4

Irrelevant Content is Discarded

Noise, off-topic sentences, and unrelated context are removed before passing to the LLM.

Python — Contextual Compression 
from langchain.retrievers import ContextualCompressionRetriever
from langchain.retrievers.document_compressors import LLMChainExtractor
from langchain_openai import ChatOpenAI

# Step 1: Create FAISS vector store from documents
embedding_model = OpenAIEmbeddings()
vectorstore = FAISS.from_documents(docs, embedding_model)

# Step 2: Create base retriever
base_retriever = vectorstore.as_retriever(search_kwargs={"k": 5})

# Step 3: Set up the LLM compressor
llm = ChatOpenAI(model="gpt-3.5-turbo")
compressor = LLMChainExtractor.from_llm(llm)

# Step 4: Wrap into Contextual Compression Retriever
compression_retriever = ContextualCompressionRetriever(
    base_retriever=base_retriever,
    base_compressor=compressor
)

# Step 5: Query the retriever
query = "What is photosynthesis?"
compressed_results = compression_retriever.invoke(query)

for doc in compressed_results:
    print(doc.page_content)  # Only relevant content!

✅ When to Use

  • Documents are long and mixed
  • Want to reduce context length for LLMs
  • Need to improve answer accuracy in RAG

⚠️ Trade-offs

  • Adds LLM call per document = more cost
  • Increases latency
  • LLM might incorrectly compress

🔧 Alternatives to LLMChainExtractor

  • EmbeddingsFilter — Faster, no LLM call
  • DocumentCompressorPipeline — Chain multiple compressors

More Retrievers in LangChain

LangChain's ecosystem includes many more specialized retrievers. Choosing the right retriever directly impacts your RAG pipeline performance.

🚀 Key Insight Better retriever → Better context for LLM → Better answers. Investing in the right retriever strategy is one of the highest-leverage improvements in Advanced RAG.
BM25Retriever

Classic keyword-based retrieval (Best Match 25). No embeddings needed. Great for exact keyword matching and traditional IR tasks.

ParentDocumentRetriever

Stores small chunks for precise retrieval, but returns the full parent document to preserve context. Best of both worlds.

TimeWeightedVectorRetriever

Combines semantic similarity with recency. Recent documents get a higher score. Ideal for news feeds, chat history, or time-sensitive knowledge.

SelfQueryRetriever

Uses an LLM to auto-generate metadata filters from your query. Enables structured filtering (e.g., "papers from 2023 about ML").

EnsembleRetriever

Combines multiple retrievers (e.g., BM25 + Vector) using Reciprocal Rank Fusion. Best for hybrid search scenarios.

MultiVectorRetriever

Stores multiple vector representations per document (summaries, chunks, hypothetical questions). Improves recall significantly.

ArxivRetriever

Directly queries the ArXiv API for academic/research papers. Returns papers as Document objects. Great for research-oriented applications.

🗺️ Quick Decision Guide

Scenario Recommended Retriever Why
Simple semantic search on custom docs VectorStoreRetriever Fast, straightforward
Need diverse, non-redundant results MMR Reduces repetition
Broad/ambiguous queries MultiQueryRetriever Wider recall via sub-queries
Long mixed-content documents ContextualCompression Cleans noise, saves tokens
Need keyword + semantic hybrid EnsembleRetriever BM25 + Vector fusion
Time-sensitive data / recent news TimeWeightedVector Boosts recent documents
Metadata-based filtering needed SelfQueryRetriever LLM-generated filters
Academic research papers ArxivRetriever Direct API access
